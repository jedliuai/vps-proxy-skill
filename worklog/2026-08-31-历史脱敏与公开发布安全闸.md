# 历史脱敏与公开发布安全闸

## 做了什么

在获得明确授权后，先做了只有本机当前用户能读取的完整私有备份，包括 Git bundle、Git 元数据和本地运行资料。bundle 校验通过，再在隔离副本里重写远端 main 的 27 个历史提交，替换已知个人标识，并将提交者统一为公共 GitHub 用户名和 noreply 邮箱。

清理后的全部可达对象通过已知隐私值和常见凭据模式扫描；最新文件树与清理前一致。39 项本地测试、静态检查和 Skill 校验通过，历史重写推送后的 GitHub CI 也通过。远端更新使用旧提交校验，避免覆盖别人刚推送的工作。

当前项目已切换到干净历史，旧本地分支、工作树和元数据转入私有备份。主工作目录里的运行配置和订阅交付文件没有改动。本次没有连接 VPS，没有变更节点、证书、密码或 Cloudflare 服务。

另外私下保存并删除了 9 条旧 GitHub Actions 运行记录：其中 8 条的提交元数据含个人标识，另 1 条仍链接重写前的历史。新历史的成功 CI 记录保留。旧日志和元数据可以从私有文件备份查阅，但删除的运行记录不能直接恢复成原 GitHub 运行。

## 为什么做

README 和 GitHub 检索标签已经准备好，但公开代码不等于公开作者的个人基础设施。只改最新文件不够，旧版本和提交邮箱同样要审查。

## 值得记住

最关键的发现是：强制推送成功之后，GitHub 仍能通过旧提交 ID 返回含个人信息的提交和文件对象。因此本阶段没有把仓库改为 Public。需要先处理平台保留对象，再重新验证公开条件；“分支里看不到”不能当作“已彻底删除”。

历史重写后的旧克隆不能直接继续推送，否则可能重新引入旧历史。以后从清理后的远端重新克隆；要恢复某项旧工作，就只取必要文件并再次审查。备份本身包含原始资料，不能上传或分享。

扫描通过只代表在已检查范围内未发现匹配项，不是对所有未知敏感信息的绝对保证。本阶段做的是仓库发布安全检查，不是一次新的服务器部署或家庭网络验收。

## 一句话亮点

让 Agent 自动化的不只是搭建节点，还有公开分享之前真正守住隐私边界。
