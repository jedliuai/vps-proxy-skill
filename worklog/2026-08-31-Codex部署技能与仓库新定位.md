# Codex 部署技能与仓库新定位

## 做了什么

把仓库从“我的美国 VPS 运维记录”扩展成了 Codex 驱动的部署工具箱。在唯一的 skill/vps-proxy-builder 里放了标准 SKILL.md、Codex 界面元数据和四份参考：准备、部署、排障、验收。根 AGENTS.md 负责让打开完整仓库的 Codex 找到这个入口，双语 README 首屏现在是一段可以直接发给 Codex 的任务提示。

不只写说明，也清理了可执行入口里的个人 SSH/domain 默认值和 Worker 模板中的个人 KV 标识；新增只读 preflight，拒绝不支持的平台、未经声明验证的管理入口、缺少授权及服务冲突。部署上传改成独立临时目录，并同时携带 Bash 与 Python 门禁。监控改成默认保留。CI 也接入了仓库检查与 Python 测试。

## 为什么做

搭节点很容易把时间消耗在细节上。希望新用户只提供 VPS、域名和必要权限，由 Codex 把技术工作做完；但不能把“自动化”误解成随便一台机器运行作者脚本，或者只装插件就自动获得云账户权限。范围收敛到 Codex，保留直连优先、Cloudflare 可选的路径。

## 值得记住的决策和坑

技能按 skill-creator 的渐进加载方式组织，不依赖一长串其他技能才能用。保留 Git/SSH/Wrangler 的可执行路径，插件只作为能力入口；插件已安装和已授权不是一回事。当前基线严格限定 Debian 13/x86_64/systemd/SSH22，ARM、其他系统和共享业务机应先做适配设计，不能绕过检查。

SSH 是最危险的一环：原脚本会关闭 root 与密码登录，因此必须先验证一条新的非 root 密钥连接和 sudo，保留控制台/救援方式。确认开关是事实声明，不是自动证明；DNS、云规则和快照还要独立核实。完整 bootstrap 不是事务，也不是日常订阅刷新按钮。

独立子 Agent 用三类新用户场景做了只读前向检查：不匹配的 root/ARM 主机、只要直连的小火箭用户、不能打断 HY2 的订阅修复。它发现直连错误路径实际返回静态页，不能照套 Worker 的404验收；还发现示例管理员名会覆盖用户自己的配置。已按证据修正文档，并补上安全导出订阅和 Windows ACL/字节保留方法。所有生成的订阅与配置副本同样是秘密，不能只保护 secrets.env。

本地门禁、入口、迁移和 Worker 测试用于检查仓库行为；模拟 Codex 不代表真的安装了一台新 VPS。本次没有连接或改动原服务器，没有部署 Cloudflare，也没有改仓库可见性。原库仍是 Private，要让陌生人的 Codex 获取，需要先授权访问或另行完成公开审查。

提交前本地 12 项门禁、4 项入口、7 项迁移、16 项 Worker 测试全部通过，技能格式、安全扫描与部署约束检查通过；README 的 GitHub Markdown 渲染结构和本地参考链接也已检查。门禁/入口测试经历了先失败再通过的过程，而不是只写完说明就宣布能部署。

## 一句话亮点

把一次搭节点的折腾，变成下一次 Codex 能沿着执行的经验；人保留选择权，机器接手重复劳动。
