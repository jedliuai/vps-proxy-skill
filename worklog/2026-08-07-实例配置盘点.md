# 实例配置盘点

## 做了什么

通过已经建立的 SSH 连接和 Google Cloud 元数据服务，把实例的云资源标识、E2 机型、
CPU、内存、系统镜像、磁盘、网络、服务账号 scope 和 Google 来宾组件都盘点了一遍，
并从本机验证了几个关键公网端口。整理结果写进了独立的实例配置报告。

## 为什么做

控制台列表只展示实例名称、区域和 IP，看不出共享 CPU 的真实份额、系统实际可用内存、
磁盘布局、代理组件以及公网暴露面。需要把“买到的规格”和“机器里实际运行的东西”放在
一起看，后续部署服务才有依据。

## 值得记住的决策、坑或技术点

- `e2-micro` 虽然系统里显示 2 个 vCPU，但持续算力合计只有 0.25 vCPU；它可以短时突发，
  不能把两个可见线程当作两颗完整 CPU。
- 机器只有约 964 MiB 系统可见内存，且没有 Swap，部署前必须留意内存峰值。
- 来宾系统只能确认启动盘属于 Persistent Disk，不能可靠识别 `pd-balanced` 等精确子类型。
- 服务账号的 OAuth scope 不允许读取 Compute API，所以没有为了“看起来完整”而猜测删除
  保护、Shielded VM、公网 IP 类型等控制面字段。
- Ops Agent 的 20201、20202 是内部自监控端口，但公网探测确认二者都能连接；需要后续
  检查 VPC 防火墙规则，不能因为它是 Google 自带进程就忽略暴露面。

## 一句话亮点

不只看控制台上的“2 核 1G”，而是把共享算力、真实资源、云代理和公网暴露一次盘清。
