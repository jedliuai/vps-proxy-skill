# 第三协议节点选型分析

## 做了什么

基于当前美国单实例、中国移动家庭网络、Mihomo 客户端和 Cloudflare 域名条件，调研并比较了 VLESS 的不同传输方式、Trojan-TLS、AnyTLS、TUIC、Shadowsocks 2022、Naive、VMess、WireGuard 以及 Cloudflare CDN/WebSocket 方案。比较重点不是协议数量，而是它们是否能覆盖不同的故障模式。

## 为什么做

现有订阅只有 Hysteria2 和 REALITY 两个节点，想知道是否值得顺手增加更多协议。当前线路的主要问题是到 Google 美国 VM 的跨境丢包，因此如果新协议仍使用同一个 IP、同一种 UDP/QUIC 或同一种非标准 TCP 端口，它通常只是多了一个名字，不会带来真正的线路冗余。

## 值得记住的决策、坑或技术点

- 当前 `美国-Reality` 已经是 `VLESS + REALITY + XTLS Vision`，并不缺 VLESS；VLESS 是代理协议，REALITY、RAW、WebSocket、gRPC 和 XHTTP 是可组合的安全层或传输方式。
- 近期最优先的工作仍应是把 ChatGPT 从 REALITY 优先改成 `US-Auto`，而不是继续增加入口。策略错误会让再多节点也发挥不了作用。
- 如果未来只增加一个第三节点，首选 `Trojan-TLS over TCP 443`：它使用标准 TCP 443 和真实证书，可与 Hysteria2 的 UDP 443 同时监听；能覆盖 UDP 被限制、TCP 2053 被针对或 REALITY 客户端兼容性异常，同时继续复用现有 Xray，维护成本最低。
- Trojan 仍与 REALITY 共用同一台 VM、同一个公网 IP 和同一条跨境路径，因此不能解决 10% 路径丢包，也不能提供国家或出口冗余。它是“协议和端口备用”，不是“线路备用”。
- AnyTLS 也是合理的 TCP 443 备选，并且 Mihomo 与 sing-box 已支持，但协议较新、需要增加 sing-box 或 Mihomo 服务端进程，证书和升级面更大；只有在明确需要服务端实现隔离时才比 Trojan 更值得。
- TUIC 与 Hysteria2 都主要基于 QUIC/UDP。虽然拥塞控制和实现不同，但面对运营商封 UDP、同一路径丢包或同一 IP 受影响时高度相关，投入产出比不高。
- Shadowsocks 2022 简单高效，但若不再叠加 ShadowTLS 等组件，伪装和主动探测韧性不如现有 REALITY/TLS 方案；叠加后复杂度又失去优势。
- Naive 的 HTTP/2/Chromium 路线有价值，但当前 Mihomo 原生代理列表并未把它作为常规出站类型，使用 sing-box/Cronet 还会引入客户端和服务端的新依赖，不适合作为 Clash Verge 的顺手第三节点。
- VLESS-XHTTP、WebSocket 或 gRPC 通过 Cloudflare 可以隐藏源 IP 并提供不同入口，但不会改变美国出口；Cloudflare 自助协议限制使用服务提供 VPN 或类似代理，WebSocket 也可能因边缘发布或空闲超时断开，因此不应把免费 CDN 当作主代理承载。Cloudflare 继续只用于订阅入口更稳妥。
- VMess、旧 mKCP 和 WireGuard 在当前场景没有提供超过现有组合的明显收益，不建议为了节点数量部署。
- 若以后实施 Trojan-TLS，需要补充证书续期后重载 Xray、未认证回落到本地 Nginx、端口级限速、独立随机密码和 ACL，并在晚高峰分别停止三个协议验证自动切换。

## 一句话亮点

真正的容灾不是把同一条路改三个名字，而是让 UDP 443、TCP 443 和 TCP 2053 各自覆盖一种不同的失败方式。
