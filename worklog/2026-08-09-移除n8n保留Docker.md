# 移除 n8n，保留 Docker

## 1. 做了什么

停止并移除了 Google Cloud 实例上的 n8n 容器、`n8n_data` 数据卷、n8n 2.32.6 镜像和
`/opt/n8n` 部署目录，同时保留 Docker Engine、Docker Compose 和其他 Docker 能力。本机也删除了
n8n MCP 配置、访问令牌环境变量、SSH 隧道进程以及两个 n8n 辅助脚本。

## 2. 为什么做

这台机器只有约 1 GB 内存，虽然配置了 2 GB Swap，但运行 n8n、任务运行器和 MCP 时仍频繁卡顿，
甚至出现 SQLite 数据库连接超时。继续维持这套服务的使用体验和维护成本都不划算，所以释放资源，
以后仍可用保留下来的 Docker 部署更轻量的服务。

## 3. 值得记住的决策、坑或技术点

- 删除范围只限 n8n；Docker Engine 和 Compose 没有卸载。
- n8n 镜像约占 2.48 GB，是这次主要释放的磁盘空间。
- 服务器保留了 `/var/backups/n8n/n8n-final-2026-08-09.tar.gz`，权限为 `0600`。
- 远程命令超时后其实仍在服务器后台继续执行，第二次备份与第一次流程发生重叠。最终归档可通过
  gzip 校验，并包含 `.env`、Compose 配置和较早的数据备份，但没有删除前最后一版 SQLite 数据库；
  最近创建的测试工作流和后续凭据不能从该归档恢复。
- 以后在低配实例上执行长时间压缩或镜像删除，应显式采用后台任务、状态文件和分阶段确认，避免把
  SSH 客户端超时误判成远端命令停止。

## 4. 一句话亮点

及时给低配云主机减负：完整下线卡顿的 n8n，保留 Docker，把 2.48 GB 空间和运行资源还给系统。
